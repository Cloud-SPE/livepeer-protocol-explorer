| TD-009 | Three post-indexer stages use row-by-row patterns where bulk SQL would be orders of magnitude faster. (1) **Valuator seed pass** (`crates/livepeer-valuator/src/seed.rs:71-147`): `fetch_candidates` returns ~2.3M rows, then loops issuing `lookup_seed → BEGIN → insert_valuation → insert_attempt → COMMIT` per event (~4-5 round-trips × 2.3M = ~1h 18m wall-clock observed on full backfill 2026-04-28). The on-chain ETH/LPT and multi-asset passes have the same shape. Bulk replacement: `INSERT INTO event_valuations SELECT … FROM raw_protocol_events r JOIN seeded_event_prices s USING (chain_id, tx_hash, asset) WHERE r.is_valuable AND r.is_canonical AND r.finality='finalized' AND r.asset IS NOT NULL ON CONFLICT DO NOTHING` runs in seconds. Same shape for the on-chain passes once `token_prices_by_block` is pre-populated per-unique-block (already wired by §11.6). (2) **Staker refresh-pending** (`crates/livepeer-staker/src/pending.rs:73-135`): walks all EarningsClaimed events (~56K), does `read_pending(pendingStake) + read_pending(pendingFees) + UPDATE` per event (~3-5 round-trips × 56K = ~3-4h wall-clock observed). Pre-compute deterministic `rpc_call_cache` keys for all (delegator, end_round, block) tuples, bulk-SELECT cached responses in one query, then one `UPDATE … FROM (VALUES …)` to apply 56K updates. Should drop from hours to ~seconds. (3) **Finality watcher** (`crates/livepeer-finality-watcher`): two `UPDATE raw_protocol_events SET finality = …` statements each touch all 2.6M rows in one statement and take ~5 minutes apiece because the predicate `EXTRACT(EPOCH FROM block_timestamp)::BIGINT <= cutoff` is non-sargable against the existing index. Either add `CREATE INDEX … ON raw_protocol_events (chain_id, is_canonical, finality, block_timestamp) WHERE is_canonical = TRUE`, or rewrite the predicate to a direct `block_timestamp <= to_timestamp(cutoff)` range comparison so the existing index serves. | S8.1, S7.2, S9.2 | medium | Open. Doesn't affect correctness (deterministic outputs identical to the loop); only wall-clock on full-history backfills. Real-data finding 2026-04-28: clean re-run post-pipeline projects to ~6.5 hours, ~95% of which is the three N+1 stages. Bulk versions would compress to minutes. Refresh-pending is enrichment-only (flow-derived stake is the load-bearing path) so the slow path is acceptable for now in production where it runs incrementally; the bulk fix is a clean-rerun accelerator. |
| TD-010 | Four API endpoints take seconds on a fully-indexed dataset (2.6M raw events / 1.1M valuations). All four are unindexed-path queries that bulk indexes / generated columns / materialized counters would fix. (1) **`/events?sort=amount_usd_desc`** (16.7s on full history): the CTE `WITH max_per_event AS (SELECT v.event_id, MAX(v.amount_usd) FROM event_valuations v WHERE v.valuation_version = $2 GROUP BY v.event_id)` (`crates/livepeer-api/src/routes/events.rs:341-346`) scans ALL 1.1M event_valuations rows even when LIMIT is small. Add a partial index `CREATE INDEX … ON event_valuations (amount_usd DESC NULLS LAST) WHERE valuation_version = 'v1_lpt_weth_twap_30min_x_chainlink_eth'` so the planner can do a top-N index scan instead of a hash aggregate. (2) **`/governance/proposals`** (5.7s on EMPTY result): `crates/livepeer-api/src/routes/governance.rs:54-80` does a self-join on `raw_protocol_events` matching `raw_event -> 'decoded' ->> 'proposalId'` on both sides — JSONB extraction is non-sargable, so the JOIN scans even when there are zero ProposalCreated rows. Either (a) add a generated column `proposal_id TEXT GENERATED ALWAYS AS (raw_event -> 'decoded' ->> 'proposalId') STORED` with an index, or (b) cache an empty-set fast path that short-circuits when no ProposalCreated rows exist. (3) **`/aggregations/events?bucket=month&metric=count&event_name=...`** (4.1s on 296k WinningTicketRedeemed rows): `crates/livepeer-api/src/routes/aggregations.rs` does a full scan of the matching event subset + date_trunc bucketing. Add `CREATE INDEX … ON raw_protocol_events (chain_id, event_name, block_timestamp) WHERE is_canonical = TRUE AND finality = 'finalized'` to support the WHERE+GROUP shape. (4) **`/backfills/status`** (1.2s): four serial `SELECT COUNT(*) FROM big_table` calls (`crates/livepeer-api/src/routes/operational.rs:61-69`). Switch to `pg_class.reltuples::bigint AS approximate_count FROM pg_class WHERE relname = 'raw_protocol_events'` for status endpoints — approximate counts are fine for an ops dashboard and return in microseconds. | S10.1, S10.2, S10.3 | low | Open.
